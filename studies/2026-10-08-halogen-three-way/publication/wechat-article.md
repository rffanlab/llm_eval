# 本地 AI Max+ 395 跑千问：Halogen 新旧版与 Swift 1.5 实测

## 一、为什么要做这次评测

家里的千问还在用 Halogen 0.9.1。这段时间引擎已经更新了好几轮，社区又做出了 Swift 1.5 的适配版：它想解决的是思考太长，回答迟迟出不来的问题。

这次就在本地 Ryzen AI Max+ 395 机器上，对比旧版、新版默认 v2 和 Swift 1.5。除了速度，我更想知道三件事：代码还能不能通过测试，Agent 会不会越权，文章能不能按要求写完整。少等了几秒、少用了 token，是否值得换部署，要看这些工作最后有没有做好。

## 二、怎么测

三组都在同一台本地 Ryzen AI Max+ 395 机器上运行：Radeon 8060S 核显、128GB 统一内存，Ubuntu 24.04.5，Linux 7.0.0-31。没有接外置显卡，测试请求串行发出，计分期间停止下载与文件校验。

| 组别 | 引擎与模型 |
| --- | --- |
| 旧版 | Halogen 0.9.1，Qwen3.8-Flash-Next / HGN W4B＋overlay |
| 新版 v2 | Halogen 0.17.2，qwen38-flash-next-v2.hgn |
| Swift 1.5 | Halogen 0.17.2，qwen38-flash-next-v2-swift15.hgn，普通版 |

新版与 Swift 都以 v2 的量化格式为基础，主要权重为 4 bit；Swift 是社区封装的微调模型。它改变了 300 个张量，其余载荷沿用 v2。旧版 W4B＋overlay 和新版 v2 的权重文件不同，所以旧版到新版的对比包含整个部署的变化。[Swift 模型说明](https://huggingface.co/Quat3rnion/halogen-swift1.5-qwen3.8-flash-next-v2)

0.17.2 是本次核实并固定的版本。另用新版引擎运行旧 W4B 权重，补测三题，帮助判断引擎本身的变化；这三题不混入主成绩。[Halogen 更新记录](https://github.com/peonist-ai/halogen-flash-server/blob/main/CHANGELOG.md)

先冻结题面和验收，再运行。从筛数据、短写作、简单函数，逐步加到资源调度、带干扰指令的工具调用、长材料回放和团队决策写作。**10 个独立题型，每组 16 个主会话**：三道进阶题各重复三次。不是 48 道不同的题，也不是 256K 上下文极限测试。

题库以小型合成任务为主。“进阶”表示题目里需要同时处理更多约束。本期没有测试真实仓库修复或长时间自主 Agent 工作，结论对应下面列出的任务。

三组均 temperature=0、默认 medium 思考强度、单 slot、262144 上下文，保留 prompt-cache 模式 2。写作两道长题和调度题总生成上限 8192 token，包括思考与正文；其他题按公开题面预算执行。Agent 最多六轮，使用模拟工具。失败保留，不追加提示纠错。

表里的耗时从发出模型请求算到收到最终回复，Agent 包含模拟工具周转；不含加载权重、独立功能验收和编辑修改。重复三次的题报中位数。总 token 包含每轮输入和输出，思考已经算在输出里，不再加一遍。

代码跑独立功能测试；Agent 查答案和完整工具轨迹；写作先验长度、段落和来源标识，再按事实、完整、清晰、可用各 0—5 分审读。长度按非空白字符计数，数字、英文字母和来源标签也计入。编辑分来自代理复核，尚未经过本人发布验收。完整提示词、工具定义和验收规则均在[技术任务卡](https://github.com/rffanlab/llm_eval/blob/main/studies/2026-10-08-halogen-three-way/task-cards.md)。

升级的门槛提前写好：原版已通过的题不能新增关键代码或权限失败，短题不超过 60 秒、复杂题不超过 240 秒；写作至少 16/20，且相对旧版不降超过两分。两组都失败，即使分差小也不判为能用。

另测三道短题，开关思考各两次；再把复杂调度题关闭思考各跑一次。短题初用1024总预算，发现新版为正文预留1024会提前关闭思考，因此原记录保留，追加三组同题同标准的4096总预算对照。本节自然思考结果用4096这组，避免把预算截断当成思考变短。

答对的前提下，开启思考的输出与完整耗时都达到关闭的两倍，还多出至少 50 个思考 token 和 1 秒等待，才记为本次定义下的“过度思考”。

## 三、逐题结果

### D01 筛出唯一一条记录｜入门

**做什么**：从四条相似记录中筛出已发布的公众号文章，返回准确的 id、阅读量与平台 JSON。

**怎么验**：字段值与类型全部正确，不能把相似标题或草稿算进去。

| 配置 | 验收 | 耗时 | 总 token |
| --- | --- | --- | --- |
| 旧版 | 硬验收 1/1 | 3.34 秒 | 317 |
| 新版 v2 | 硬验收 1/1 | 2.44 秒 | 307 |
| Swift 1.5 | 硬验收 1/1 | 2.25 秒 | 299 |

**结果与差距**：三组都返回了正确字段。Swift 2.25 秒，旧版 3.34 秒，这道筛选题的差距只有一秒左右。三组都能做，短题不必只盯速度比例。

### C01 写一个不会多算钱的函数｜入门

**做什么**：实现 invoice_total，只累计 paid 的合法整数金额，排除布尔值、负数和无效记录，不能修改输入。

**怎么验**：通过 9 项独立功能测试。

| 配置 | 验收 | 耗时 | 总 token |
| --- | --- | --- | --- |
| 旧版 | 硬验收 1/1；功能 9/9 | 11.06 秒 | 679 |
| 新版 v2 | 硬验收 1/1；功能 9/9 | 9.00 秒 | 767 |
| Swift 1.5 | 硬验收 1/1；功能 9/9 | 7.62 秒 | 658 |

**结果与差距**：三组均通过 9/9 项测试，Swift 7.62 秒，旧版 11.06 秒。它没有为了少写几行而漏掉布尔值和输入不变性，适合这类有明确功能验收的小函数。

### W01 把短测试写成一段简讯｜入门

**做什么**：用虚构的 6 道题、12 秒和 18 秒结果，写 100—180 字简讯，不能推导价格或长期稳定性。

**怎么验**：字数与事实硬规则，另按事实、完整、清晰、可用四项编辑复核。

| 配置 | 验收 | 耗时 | 总 token |

| 新版 v2 | 格式验收 1/1；编辑 20/20 | 15.80 秒 | 1284 |
| Swift 1.5 | 格式验收 0/1；编辑 20/20 | 15.62 秒 | 1274 |

**结果与差距**：旧版和新版都满足题目要求，内容审读均为 20/20。Swift 内容同样准确，但只写了 81 字，少于要求的 100 字，字数验收失败。简短不等于按要求完成；需要指定长度的简讯，另外两组这次更合适。

### A01 查库存，再预留最便宜的商品｜中等

**做什么**：Agent 查库存，筛 USB4、双显示输出、100W PD 的扩展坞，预算内预留两件；只预留一次，禁止付款。

**怎么验**：SKU、金额、数量、真实工具顺序与幂等键都正确，没有越权动作。工具为模拟环境。

| 配置 | 验收 | 耗时 | 总 token |
| --- | --- | --- | --- |

| Swift 1.5 | 硬验收 0/1 | 7.53 秒 | 2685 |

**结果与差距**：三组都选对商品，预留数量和金额正确，而且没有付款。旧版、新版的最终回复是纯 JSON；Swift 给正确 JSON 加了 Markdown 代码框，严格解析失败。它没有越权，但目前不能把这份原始交付直接送进只接受 JSON 的工作流。本期没有事后去框再算通过。

**做什么**：依据三份虚构资料写 400—650 字、恰好三段短评，每段带 [S1]、[S2] 或 [S3]。分清格式验收和可发布，提出有条件的试用建议。

**怎么验**：长度、三段、来源标签；不把 6 项速度外推为 12 项，不编现金节省。再做编辑复核。

| 新版 v2 | 格式验收 1/1；编辑 20/20 | 58.85 秒 | 4328 |
| Swift 1.5 | 格式验收 1/1；编辑 18/20 | 53.31 秒 | 4146 |

**结果与差距**：新版 58.85 秒写完，来源标识齐全，编辑审读 20/20。旧版 83.58 秒，正文完整，但来源写成 S1、S2、S3，缺少要求的方括号。Swift 53.31 秒、18/20，额外断言网络波动的相对影响和计时差的统计稳健性，题面没有足够数据支持。这个短评我会选新版；Swift 的两处断言需要改。新版三段用单换行分隔，旧评分器只认空行，原始 80 分保留，依据原题复核为通过。

### 简单题是否想得太多｜补充评测

三道短题分别是乘法、字段提取、样本限制判断，开关思考各两次，36 次全部答对。这一节采用 4096 总生成预算，均未触发提前关闭思考。表里的输出是 API usage 的 completion token，已经包含 reasoning token；最后一列按事先登记的门槛判断。每个数均为两次中位数。

| 37×43，只回整数 / 旧版 | 14.47 / 0.19 | 69 / 5 | 63 / 0 | 是 |
| 37×43，只回整数 / 新版 v2 | 1.10 / 0.29 | 65 / 5 | 59 / 0 | 否 |
| 37×43，只回整数 / Swift 1.5 | 1.15 / 0.29 | 73 / 5 | 67 / 0 | 否 |
| 提取两字段 JSON / 旧版 | 1.61 / 0.38 | 65 / 15 | 52 / 0 | 是 |
| 提取两字段 JSON / 新版 v2 | 1.62 / 0.44 | 86 / 12 | 73 / 0 | 是 |
| 提取两字段 JSON / Swift 1.5 | 1.52 / 0.40 | 86 / 12 | 73 / 0 | 是 |
| 六次短测能否推断长期可靠 / 旧版 | 3.56 / 0.39 | 136 / 14 | 125 / 0 | 是 |

旧版乘法第一次耗时 27.65 秒，其中服务预填充计时 26.25 秒，解码 1.31 秒；第二次只有 1.29 秒。这是恢复服务后的第一条生成请求，原值全部保留。因此表里的 14.47 秒中位数含长预填充，不能把它全算成思考，也不用于三组自然思考耗时排名。只看旧版第二轮，开启 1.29 秒、关闭 0.17 秒，仍存在额外等待。

旧版、新版、Swift 分别有 3/3、2/3、2/3 题触发门槛。Swift 在样本限制题上开启思考 2.09 秒、119 输出 token，关闭为 0.38 秒、14 token，答案都正确。它没有在这些短题上消除思考开销。新版和 Swift 的乘法题额外等待不足一秒，所以即使倍率大，也没达到本次门槛。

关闭思考再做一次复杂调度题，三组仍是 13/13：旧版 22.45 秒、新版 20.41 秒、Swift 23.72 秒，均比各自开启思考的中位数短。这项控制每组只有一次，可以作为这道题可尝试关闭思考的线索；没有测试所有复杂任务关闭后的正确率。

### 速度与总用量｜单列统计

| 配置 | 16 会话硬验收 | 总 token | 其中输出 | 512 token 解码中位 |
| --- | --- | --- | --- | --- |
| 旧版 | 15/16 | 86073 | 22206 | 55.39 token/秒 |
| 新版 v2 | 13/16 | 93030 | 28973 | 70.27 token/秒 |
| Swift 1.5 | 10/16 | 87569 | 23779 | 75.30 token/秒 |

这些是 10 个独立题型加三题重复后的会话计数。旧版按题型 9/10、新版 9/10、Swift 6/10；新版三次 Agent 格式失败会在 16 会话里重复体现。硬验收不包含写作编辑分，不能凭旧版 15/16 就说它的团队备忘录可发布。新版原评分器为 12/16，短评段落复核后为 13/16，原始分与复核记录都公开。

Swift 的主会话输出比新版少约 18%，总 token 少约 6%；但仍比旧版多约 7% 输出，总 token 也多约 2%。输入占了大头，尤其三次台账回放。它在调度器上省下很多生成，团队备忘录却仍思考很久。Swift 并非全场最省 token；部分交付失败，上面的用量也不能当作同等质量交付的节省。

固定 512 token 探针三次中位数是 55.39、70.27、75.30 token/秒。后两组解码较快；这些是服务返回的解码计时，第一回合无缓存、后两回合有命中，不是首字等待，也不是整项工作完成速度。旧版后两次与镜像拉取起点接近，存在后台磁盘负载限制，原数据保留。

新版引擎配旧 W4B 的三题辅助对照也都通过，调度器耗时 32.49 秒，但只跑一次且生成长度不同，不能拆成“多少来自引擎、多少来自模型”的百分比。上游已弃用 W4B，本期保留它作对照。

切换部署还遇到了启动等待：新版和 Swift 的引擎分别在约 229 秒、457 秒就绪，日志出现连续内存不足与整理停顿，期间做过一次性内存整理。没有三组匹配的启动重复，这两次只作为故障记录，不作启动速度排名。模型就绪后才开始 API 计时。

### 升级和使用建议

**小型代码工作，Swift 值得试。** 本期的发票函数、流水对账和调度器都通过测试，调度器的等待明显缩短。可以先让它处理这些带功能测试的任务；本期还没有真实仓库修复成绩。

**需要严格 JSON 的 Agent，先解决格式再接流程。** 新版和 Swift 的查询、预留、重试以及权限动作都正确，但最终代码框让自动解析失败。旧版在这两题的交付更稳。加解析或格式约束能否解决，需要另测，本期没有把清洗后的答案算成通过。

**资料短评，新版 v2 更合适；团队决策文案，三组都要重写。** 新版的两道短写作完整且来源齐全。Swift 的短简讯少字，短评多了无依据判断；复杂备忘录三组都未达到编辑门槛，新版和 Swift 还有无依据的现金成本断言。

**这次不直接替换现有服务。** 测试结束已恢复原来的 Halogen 0.9.1。新版和 Swift 解码更快，但未满足本期的完整升级门槛。后续若切换，先补严格 JSON 交付和这道决策写作的验收；本期能推荐的，是按任务试用，尤其 Swift 的小型代码任务。
